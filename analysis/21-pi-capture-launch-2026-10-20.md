# Pi 抓包启动与进程退出

## 现场证据与失败链路

用户截图显示同一失败会话已经记录 `GET https://pi.dev/api/latest_version`，状态 200，随后出现 `capture_launch_unverified`，会话显示零个初始进程。另一张截图中 Pi 已打开，模型请求反复 `fetch failed`。

这说明代理已就绪且 Pi 至少完成过一次网络请求，失败点是新进程绑定。原 `launch_with_proxy` 在终端启动后，用全局 Agent matcher 与启动前列表之差识别新实例；超时返回错误，外层 Worker 被释放并终止抓包代理。已经启动的 Pi 仍持有该代理地址，后续请求因此可能连接失败。截图没有底层网络错误，不能据此排除额外的证书或上游问题。

Pi 官方 1.3.0 的 `setupCli` 会设置 `process.title = APP_NAME`。原 matcher 对标题回退要求启动入口是 JS 文件，且参数全文等于标题；安装包装器或不同参数表示会使识别失败。用户机器具体安装入口尚未取得，不能断言命中了其中哪一种情况。

## 修复

- 新启动的 CLI 通过 Arca 私有目录中的一次性文件报告自身 PID 与启动时间，再 `exec` 原启动命令。参数按 argv 传递，保留已有代理与证书环境；不记录命令、环境或凭据。父进程按报告的 PID 和启动时间绑定，子进程沿该根跟踪。GUI 应用仍使用原实例发现逻辑。
- PID 交接目录权限 0700，文件由 shell 以 0600 和禁止覆盖方式创建；绑定完成或失败后清理。待绑定引擎的期限覆盖终端派发与交接各自的超时。
- Rust 与 Python 的进程检查排除僵尸及死亡状态。目标退出后先收尾请求，再清空当前 PID 并停止引擎。
- Core 在读取会话和开始下一次记录时独立核验选定 PID 的身份，防止后台 watcher 未及时退出时遗留 `capture_busy`。其他 Arca 进程拥有的会话只通过既有停止标记请求收尾。
- 抓包设置打开时每两秒刷新进程列表。

## 当前验证

- Rust CLI 编译、TypeScript/Vite 生产构建通过。按仓库默认没有运行 cargo/npm 测试套件。
- 隔离安装官方 Pi 1.3.0 和 mitmproxy 12.2.1，使用无外部调用的本机模型端点。实际 Pi 经代理完成 HTTP 请求及 SSE，返回 `OK`，记录为 200 / complete。
- 再用原样提取的启动交接 shell 片段启动一个 Pi 包装器，PID 与实际子进程一致；使用本机 HTTPS 模型端点、额外 CA 和上游证书校验，Pi 返回 `OK`，HTTPS 请求记录为 200 / complete。
- Pi 退出后未立即回收其进程，watcher 仍识别退出，会话转为 stopped 且当前 PID 列表为空。
- 通过编译后的 CLI 读取隔离会话：保留一个实际已退出、尚未回收的目标进程，并让 runtime identity 仍指向存活进程。Core 返回 stopped、清空当前 PID，并创建安全停止标记；不会仅凭引擎存活继续显示记录中。这是针对状态读取的隔离检查，不等同于真实引擎运行证据。

运行环境是 Linux。复现中仅用返回不可用的替身替代 macOS `proc_pidpath`，目标绑定使用实际 PID；Pi、mitmproxy、TLS 与请求转发均真实运行。这些结果不等同于 macOS Terminal 自动化、官方 App 内的完整启动或用户真实模型供应商验收。正式交付以 Git 历史和 Release 为准，本记录不替代用户机器上的安装验收。
