# Provider Catalog sources

## Fortytwo Engine — 2026-11-10

`fortytwo-engine` / `Fortytwo Engine` is a gateway Provider for [Fortytwo Engine](https://engine.fortytwo.network/), Fortytwo's OpenAI-compatible inference API for open-weight models. The [quickstart](https://docs.fortytwo.network/docs/quickstart), [API conventions](https://docs.fortytwo.network/apis/api-reference-intro), and [OpenAI compatibility](https://docs.fortytwo.network/docs/openai-compatibility) set the base URL to `https://api.fortytwo.network/v1`. They document `POST /v1/chat/completions` with `Authorization: Bearer`. The OpenAI SDK examples use that base URL. Arca stores Chat Completions on `https://api.fortytwo.network/v1` (that base plus `/chat/completions`). [Get access](https://docs.fortytwo.network/docs/access) says keys start with `sk-ft-v1-` and are sent on `Authorization`. It does not document `x-api-key`.

[OpenAI compatibility](https://docs.fortytwo.network/docs/openai-compatibility) lists `POST /v1/chat/completions` and `GET /v1/models` as supported. It says Responses, Completions, Embeddings, Audio, Images, Files, Batches, Fine-tuning, Moderations, Assistants, and `GET /v1/models/{id}` are not supported (`404`). The [Codex guide](https://docs.fortytwo.network/agents/codex) says Codex needs the Responses API, so it runs a local LiteLLM proxy that translates Responses to Chat Completions. No Anthropic Messages or Gemini generateContent contract is documented. Arca does not store Responses, Anthropic Messages, or Gemini.

Probes on 2026-11-10: `GET /v1/models` and `POST /v1/chat/completions` with no key return HTTP 401 `invalid_api_key` (`The API key is missing or not valid.`). A bogus Bearer key on those routes returns that same 401. A bogus `x-api-key` on both routes returns that same 401 text, so this probe does not show whether `x-api-key` was read. `POST /v1/responses` and `POST /v1/messages` with no key, and the same requests with a bogus Bearer key, return HTTP 404 with an empty body. `POST /v1/messages` with a bogus `x-api-key` returns that empty 404. `POST /v1/completions` and `POST /v1/embeddings` with a bogus Bearer key return that empty 404. `GET /v1/nonexistent` returns that empty 404 with no key and with a bogus Bearer key. `GET /v1/models/qwen/qwen3.8-27b` with no key, and `POST /v1beta/models/qwen/qwen3.8-27b:generateContent` with no key and with `x-goog-api-key`, return that empty 404. `OPTIONS /v1/chat/completions` returns HTTP 405 with an empty body. `GET /`, `GET /models`, and `POST /messages` return HTTP 404 `404 page not found` (`text/plain`). Responses, Completions, Embeddings, Messages, and Gemini are not stored.

Model discovery uses the OpenAI catalog decoder with a required credential. [List models](https://docs.fortytwo.network/apis/get-models) and the [models guide](https://docs.fortytwo.network/docs/models) document `GET /v1/models` as `{object: "list", data: [{id, object: "model", created, owned_by}]}` and require a bearer key. The published example is `qwen/qwen3.8-27b` with `owned_by` `fortytwo`. The live authenticated body was not observed. The decoder reads `id` and `name`. Documented entries have no `name` and no context field, so a model discovered with a key does not carry a context length from this list. With no credential, Arca does not call the network. The seed is the only row on the models page: `qwen/qwen3.8-27b` (Qwen3.8-27B), context 262,144. That page also states max output 235,929. The catalog summary has no max-output field, so 235,929 is not stored. The [engine page](https://engine.fortytwo.network/) prints the same context window and max output.

The models page says this model accepts text and image input, text output, streaming, reasoning effort, tool calling including parallel calls, and structured output `json_object` or `json_schema` with `strict: true`. [Image input](https://docs.fortytwo.network/docs/images) accepts PNG and JPEG by HTTPS URL or base64 data URL. The engine page also lists WebP. The image guide does not, so WebP is not treated as supported. The catalog does not encode features.

Pricing disagrees across official pages on this date. [Pricing](https://docs.fortytwo.network/docs/pricing) lists `qwen/qwen3.8-27b` at $0.425 / 1M input tokens, $0.085 / 1M cached input tokens, and $2.55 / 1M output tokens, and says reasoning tokens are billed as output. The engine page model specs show cache read, input, and output at $0 / MTok and do not state a duration. [Promotional credits](https://docs.fortytwo.network/docs/promotional-credits) describes promo codes and offers and does not name this model or a 24-hour window. A public page stating that Qwen3.8-27B is free for 24 hours from 2026-11-10 12:00 UTC was not found. The catalog does not encode either price.

[Tiers and limits](https://docs.fortytwo.network/docs/limits) says every account starts on Core: 20 requests per minute and 500 per hour, per model. Pro is 200 / 7,000 after $500 of spend in a calendar month, and Scale is 600 / 20,000 after $10,000. The engine page prints those same three rate-limit rows. The catalog does not encode the quota.

Only `api.fortytwo.network` is mapped for host inference. `engine.fortytwo.network` serves the product site (`GET /v1/models` there is the site HTML, HTTP 404). `fortytwo.network` is the marketing site, and `www.fortytwo.network` redirects to it. `docs.fortytwo.network` is the documentation site. `platform.fortytwo.network` is the account app. Those stay `custom`, as do lookalikes. `www.api.fortytwo.network` did not resolve. The platform bundle's static routes include `/api-keys`. An unsigned GET of <https://platform.fortytwo.network/api-keys> returns the login page with `redirect=/api-keys`. The template portal is that URL with kind `api-key`.

## Eden AI — 2026-11-08

`edenai` / `Eden AI` is a gateway Provider for [Eden AI](https://www.edenai.co/docs/). The [chat completions](https://www.edenai.co/docs/v3/llms/chat-completions) guide and the published [OpenAPI](https://api.edenai.run/v3/docs/openapi.json) set the OpenAI-compatible base to `https://api.edenai.run/v3` on server `https://api.edenai.run`. They document `POST /v3/chat/completions` with `Authorization: Bearer` (`AuthBearer`). The OpenAI SDK examples use `base_url` `https://api.edenai.run/v3`. Arca stores Chat Completions on that base with `/chat/completions`. Model ids in the default catalog are `provider/model` endpoint ids. A name without a provider is a routable alias and is not a separate default-catalog id.

[Responses](https://www.edenai.co/docs/v3/llms/responses) documents `POST /v3/responses` on the same base. The OpenAPI lists that path, plus retrieve and delete. `store` defaults to `true`. The guide says to pass `store: false` to stay stateless, and it does not require that value or reject `store: true`. Arca stores Responses on `https://api.edenai.run/v3` and does not declare a storage override. [Create Anthropic Message](https://www.edenai.co/docs/api-reference/anthropic-messages/create-anthropic-message) documents `POST /v3/v1/messages` with the same bearer scheme. The [Claude Code](https://www.edenai.co/docs/v3/integrations/claude-code) guide sets `ANTHROPIC_BASE_URL` to `https://api.edenai.run/v3` and says the client appends `/v1/messages`. It says `ANTHROPIC_AUTH_TOKEN` is sent as `Authorization: Bearer` and that `ANTHROPIC_API_KEY` also works. Arca stores Anthropic Messages on that same base, so the client base stays `https://api.edenai.run/v3` and the path is `/v1/messages`. No Gemini generateContent contract is documented, so Gemini is not stored.

## Native protocol additions — 2026-10-26

Google AI Studio supports [Interactions](https://ai.google.dev/gemini-api/docs/interactions-overview)
at `POST /v1beta/interactions` (`model`, `input`, `x-goog-api-key`). New connections
prefer this protocol while retaining generateContent. Arca's cURL examples opt
out of stored interaction state with `store=false`; the Models catalog remains
the Google `GET /v1beta/models` endpoint. Selecting `@ai-sdk/google` alone does
not select the separate `google.interactions(...)` factory, so Arca's current
Agent writers must reject Interactions assignment rather than emit generateContent.
This boundary was checked against OpenCode's current stable
[v1.19.4 provider loader](https://github.com/anomalyco/opencode/blob/v1.19.4/packages/opencode/src/provider/provider.ts),
which calls `sdk.languageModel(...)`. Its dev-branch v2 native Interactions
provider is not a supported stable-client contract.

Amazon Bedrock [Converse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)
uses the regional `https://bedrock-runtime.<region>.amazonaws.com` endpoint and
`POST /model/{model}/converse`. Its content-block `messages` body has no `model`
field. The [official API-key workflow](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-use.html)
supports Bearer authentication. Arca reuses its current Keychain/environment/file/helper
credential sources for this key without adding IAM credential administration.
The [Amazon Bedrock AI SDK provider](https://ai-sdk.dev/providers/ai-sdk-providers/amazon-bedrock)
supports `baseURL` and Bearer `apiKey`, which are mapped by the OpenCode/Kilo writers.
Converse model discovery is manual; it must not probe a fabricated `/models` route.
